# Краткое ТЗ

Обновлено: 2026-09-05

## Задача

Разработать прототип инструмента автоматизированного agentic red teaming, который находит и демонстрирует многошаговые атаки на LLM-агента с постоянной памятью. Допустима доработка существующего open-source инструмента или собственный прототип.

Главный вопрос проверки: можно ли незаметно изменить состояние агента так, чтобы в последующей сессии он выполнил выгодное атакующему действие?

## Пользователь

Департамент кибербезопасности, валидирующий системы генеративного ИИ до внедрения и после изменений модели, промптов, памяти или инструментов.

## Объект наблюдения

Проверяется не только пара «запрос - ответ», а цепочка:

`input -> context -> memory -> planning -> tool choice -> tool arguments -> tool result -> state change -> later action`

Каналы доставки: пользовательский запрос, документ, веб-страница и результат инструмента. Существенные эффекты: изменение памяти/состояния, перенос между сессиями или пользователями, изменение решения, вызова инструмента либо его аргументов, дальнейшее распространение компрометации.

## Обязательный цикл продукта

1. Анализ приложения и моделирование угроз.
2. Генерация многошагового сценария атаки.
3. Выполнение атаки на агенте.
4. Сбор трассы и снимков состояния.
5. Проверка достижения цели по наблюдаемым доказательствам.
6. Анализ скомпрометированного состояния.
7. Воспроизводимый отчёт.

## Целевая метрика

Основная метрика из ТЗ - Attack Success Rate (ASR), доля успешных атак. Для stateful-атак ASR необходимо считать по полной цепочке до проверяемого последствия, а промежуточные этапы показывать отдельно.

## Тестовый объект

Локальный стенд `m-melgizin/genai-invest-agent-memory-stand`:

- OpenAI-compatible agent API;
- Redis для рабочей памяти;
- MongoDB для диалоговой, эпизодической, семантической и глобальной policy memory;
- MCP/REST инструменты инвестиционного ассистента;
- режимы `vulnerable` и `protected` для сравнения;
- пять синтетических пользователей и синтетические банковские данные.

## Критерии готовности MVP

- Один сценарий воспроизводимо проходит стадии injection -> persistence -> new session/user -> retrieval -> tool/state consequence.
- Для каждого прогона сохраняются конфигурация, seed, события, снимки/дифф памяти, tool calls и вердикты.
- Программный oracle подтверждает запись и конечное последствие; LLM judge применяется только там, где недостаточно структурных данных.
- Одинаковая кампания запускается в `vulnerable` и `protected` режимах и показывает различие.
- Отчёт содержит ASR и воронку стадий, а не только ответы модели.

## Зафиксированный scope

Разрешён только локальный намеренно уязвимый стенд и синтетические данные. Реальные банковские системы, аккаунты и данные не входят в scope. Действия, меняющие внешние системы, не требуются.

## Открытые организационные вопросы

- дедлайн, формат и длительность защиты;
- доступные вычислительные ресурсы и разрешённые LLM-провайдеры;
- точный evaluator организаторов и вес критериев помимо ASR;
- требуется ли доработка конкретного open-source продукта;
- можно ли включать созданный корпус атак в итоговую поставку.
